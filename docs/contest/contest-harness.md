# Contest Submission Harness — 2026 모두의 AI 실험실

## 1. 최상위 목적

이 저장소의 현재 단기 목적은 **2026 모두의 AI 실험실 AI 서비스 경진대회에 제출할 실행 가능한 MVP와 제출 증빙을 완성하는 것**이다.

마감: **2026-09-06 18:00 KST**

공모전 서비스:

> **시니어 AI 생활매니저 — 안심부터 시작하는 시니어 디지털 동행**

현재 세션에서는 장기 제품 확장보다 공모전 제출 완료가 우선한다.

### Product Boundary — 반드시 유지

**제품은 `시니어 AI 생활매니저`다. `안심매니저` 또는 `Trust Check`가 제품 전체가 아니다.**

- 안심/위험 확인은 생활매니저가 모든 생활 장면에서 지켜야 하는 **공통 안전 원칙**이다.
- Trust Check는 현재 가장 완성도가 높은 **첫 번째 생활 장면**이다.
- Hospital Kiosk Safe Guidance는 같은 생활매니저가 다른 생활 장면에서도 작동함을 보여주는 **두 번째 대표 장면**이다.
- 제품 방향은 문자 → 키오스크 → 예약/일정 → 행정·생활지원 → 필요 시 가족/사람 연결로 확장한다.
- 제출문서는 구현 범위와 확장 방향을 정확히 구분하되, **사용자 화면은 완성된 제품처럼 보여야 한다.**
- 구현되지 않은 예약/일정·행정/생활지원 기능은 사용자 화면에서 `준비 중`처럼 자연스러운 제품 언어로만 표현하고 구현 완료로 주장하지 않는다.

### User-facing language rule — 제품 화면과 내부 문서를 분리

아래 표현은 **내부 개발/공모전 문서에서만 사용**하고 사용자 화면에는 노출하지 않는다.

- `공모전`, `출품`, `MVP`
- `프로토타입`, `데모`, `시연`
- `실제 구현`, `구현 완료`, `구현 상태`
- `확장 방향`처럼 개발 로드맵을 직접 드러내는 표현

사용자 화면에서는 다음처럼 제품 언어를 사용한다.

- 현재 가능한 기능: `지금 이용`, `바로 이용 가능`
- 아직 제공하지 않는 기능: `준비 중`
- 제한사항: 구현 변명이 아니라 사용자에게 필요한 사실만 설명
  - 예: `개인정보는 대신 입력하거나 저장하지 않습니다.`

**심사위원에게 보여주는 화면도 사용자에게 판매·배포할 제품 화면과 동일한 기준으로 작성한다.**

출품 내용, UI, README, 발표자료가 `안심매니저` 단일 제품처럼 읽히면 **제품 정체성 오류**로 간주하고 수정한다.

## 2. MVP 정본

MVP는 이 저장소 `Lightning-Public/senior-trust-gateway`의 실행 가능한 프로토타입이다.

두 개의 앱을 새로 만드는 것이 아니다.

### 메인 흐름 — Trust Check 80%

```text
문자/디지털 요청 입력
→ 의미 이해
→ 결정론적 위험 확인
→ 쉬운 다음 행동
→ 필요 시 가족/사람 확인
```

### 확장 흐름 — Hospital Kiosk Safe Guidance 20%

```text
병원 접수 시작
→ 예약 진료 선택
→ 민감정보 단계 감지
→ HIGH 안전 중단
→ 직원 도움 안내
```

두 흐름은 하나의 생활매니저 정책을 공유한다.

> `이해 → 위험 확인 → 쉬운 다음 행동 → 필요 시 사람 연결`

## 3. 공모전 제출에서 aitestbed의 역할

aitestbed는 **MVP를 대신 만드는 주체가 아니다.**

현재 confirmed인 역할:

- 바이브코딩 사용 이력과 결과를 공모전 활용 증빙으로 확보
- 필요 시 UI 아이디어/생성 결과를 현재 MVP와 비교
- 생성 소스가 있으면 필요한 부분만 최소 포팅
- 클라우드/플랫폼 이용 사실을 증빙

현재 unverified인 역할:

- 외부 프로젝트에서 aitestbed 모델을 직접 호출하는 AI 추론 API

`AitestbedModelApiProvider`는 공식 호출 계약과 실제 probe를 확인하기 전에는 구현하지 않는다.

**기존 MVP가 정본이고, aitestbed 생성 결과는 보조 참고물이다. 생성 결과로 현재 안전정책·아키텍처·저장소 구조를 교체하지 않는다.**

## 4. 현재 작업 우선순위

## 5. Scope Gate

새 작업을 시작하기 전에 반드시 아래 질문을 통과해야 한다.

> 이 작업이 **(a) 실행 가능한 MVP**, **(b) 제출문서**, **(c) 필수 플랫폼 증빙** 중 하나를 직접 개선하는가?

- YES → 진행 가능
- NO → 공모전 이후 backlog로 이동

### 지금 하지 않는다

- 새로운 제품/앱 추가
- 대시보드/관리자 기능 추가
- 여러 Kiosk 시나리오 추가
- 두 저장소 전면 통합
- 장기 Life OS 기능 개발
- 확인되지 않은 AI API adapter 구현
- CV/OCR/image input 구현
- 결제/계정변경/실제 개인정보 처리
- 공모전 제출에 필요 없는 구조 리팩터링

## 6. 사실 경계

항상 다음을 분리한다.

### 구현됨

실제 저장소 코드와 테스트로 확인된 것만 사용한다.

### 플랫폼에서 확인됨

실제 aitestbed 화면/공식 문서에서 본 값만 사용한다.

### 후보/미확인

화면·공식 문서·실제 호출로 확인되지 않은 기능은 `candidate` 또는 `blocker`다.

특히 다음 불변식을 유지한다.

- `AI confidence != user authorization`
- `Risk != Verification`
- 공식 목록 미일치 != 안전
- 규칙엔진 HIGH는 AI가 낮추거나 승인할 수 없음

## 9. MVP 제출 완료 기준

### 제품

- 첫 화면에서 `시니어 AI 생활매니저`의 생활지원 정체성이 이해됨
- 사용자 화면에 공모전/개발 내부 용어가 노출되지 않음
- Trust Check가 실제 실행됨
- LOW/MEDIUM/HIGH와 안전한 다음 행동이 표시됨
- HIGH 안전정책이 유지됨
- 병원 Kiosk 한 시나리오가 시작 → HIGH 안전중단까지 재현됨
- Trust Check와 Hospital Kiosk가 별도 앱이 아니라 하나의 생활매니저 경험으로 연결됨
- 향후 예약/일정·행정/생활지원은 자연스러운 제품 언어로 현재 제공 기능과 구분됨
- 확인되지 않은 외부 AI API 없이도 MVP가 깨지지 않음

### 검증

- 모든 테스트 통과
- production build 통과
- GitHub CI green

### 제출 증빙

- 서비스 문제/해결 흐름 설명
- MVP 화면 캡처
- aitestbed 실제 사용 증빙
- 실제 확인된 플랫폼 사실과 미확인 기능 분리
- AI 활용과 결정론적 안전정책의 역할 분리 설명

### 제출물

- 제출 문서가 현재 코드와 일치
- 미구현 기능을 구현 완료로 주장하지 않음
- 최종 PDF/PPT/PPTX와 제출 체크리스트 완성
