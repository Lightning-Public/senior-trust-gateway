# AI 활용 필요성·플랫폼 활용·안전 설계

`시니어 AI 생활매니저`가 해결하려는 문제는 고령자가 문자, 키오스크, 공공·생활 서비스 같은 디지털 환경에서 “이 내용을 믿어도 되는가, 지금 무엇을 해야 하는가”를 매번 스스로 판단해야 한다는 점이다. 기존 규칙엔진은 송금·인증번호·앱 설치·원격제어처럼 명확한 위험 신호를 빠르고 일관되게 차단할 수 있지만, 가족 사칭 가능성, 기관 안내, 복잡한 키오스크 화면처럼 문맥을 이해해야 하는 상황에는 한계가 있다. 따라서 AI는 **애매한 의도와 상황을 이해하고 60대 이상 사용자가 이해하기 쉬운 설명으로 바꾸는 역할**에 사용하되, 안전 권한은 AI와 분리한다.

공모전 MVP의 정본은 `Lightning-Public/senior-trust-gateway`의 실행 가능한 prototype이다. Phase 0은 Trust Check 80% + Hospital Kiosk Safe Guidance 20%로 제한한다. 병원 Kiosk 데모는 카메라/CV/OCR 없이 접수 시작과 예약 선택을 안내하고, 주민등록번호 전체 입력 같은 민감정보 단계에서는 HIGH로 자동 진행을 중단해 직원 도움을 요청한다. 두 장면은 별도 앱이 아니라 `이해 → 위험 확인 → 쉬운 다음 행동 → 필요 시 사람 연결`을 공유한다.

서비스는 AI와 안전정책의 역할을 의도적으로 분리한다. Senior Trust Gateway는 위험등급, 공식 검증 수준, 권한정책과 사람 에스컬레이션을 담당한다. AI context layer는 `AIProvider` 경계를 통해 문맥 이해와 쉬운 설명을 담당할 수 있다. AI 출력 계약은 `summary`, `risk_context`, `safe_next_action`, `uncertainty`이며, 송금·이체·인증번호 전달·앱 설치·원격제어·개인정보·결제처럼 고위험 행동은 규칙엔진의 HIGH 판정을 AI가 낮출 수 없다. 즉 **AI confidence != user authorization**을 제품 정책으로 구현한다.

현재 AI context layer는 코드와 테스트로 안전계약·fallback이 검증됐지만, 공식 호출 계약이 확인된 실제 외부 AIProvider가 없어 기본 MVP UI 실행 경로에는 외부 AI 호출을 연결하지 않았다. 이를 실제 모델 API 연동 완료로 주장하지 않는다. 확인된 provider가 생기면 server-side 경계 뒤에 연결하고, timeout·quota·잘못된 JSON·모델 장애에서는 결정론적 결과로 fallback한다.

모두의 AI 실험실(aitestbed)의 현재 확정 역할은 **플랫폼 활용 증빙과 바이브코딩 생성·수정·소스 다운로드 경험의 증빙**이다. aitestbed가 현재 MVP를 대신 만드는 것은 아니다. 생성 결과가 확보되면 현재 MVP와 비교해 접근성·레이아웃 등 필요한 UI 개선만 최소 포팅한다. `AitestbedModelApiProvider`는 공식 AI 추론 API 문서, base URL/인증/schema, 최소 실제 호출 probe, 외부 사용·개인정보·상업 이용 범위가 확인된 경우에만 구현한다.

이 구조는 공모전의 **문제 정의 및 제안 필요성**에는 고령자의 디지털 신뢰·접근성 문제로, **창의성 및 AI 활용 적절성**에는 AI의 문맥 이해와 결정론적 권한통제를 결합한 구조로, **실현 가능성 및 완성도**에는 동작하는 Trust Check·Hospital Kiosk 안전 흐름·AI 안전계약·fallback 테스트·CI와 실제 aitestbed 활용 증빙으로 대응한다.

공모전 제출까지의 우선순위는 `실행 가능한 MVP → test/build/CI → 제출문서와 코드 일치 → aitestbed 활용 증빙 → 최종 제출물`이다. 장기적으로는 문자와 키오스크를 시작으로 예약·행정·생활지원·가족 연결까지 확장하지만, 공모전 제출 전에는 해당 장기 기능을 개발 범위에 넣지 않는다.
