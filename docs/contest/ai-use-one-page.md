# AI 활용 필요성·플랫폼 활용·안전 설계

`AI 안심매니저`가 해결하려는 문제는 시니어가 문자 한 통을 받았을 때 “이 말을 믿어도 되는가, 지금 무엇을 해야 하는가”를 스스로 판단하기 어렵다는 점이다. 기존 규칙엔진은 송금·인증번호·앱 설치·원격제어처럼 명확한 위험 신호를 빠르고 일관되게 차단할 수 있지만, “휴대폰을 잃어버려 번호가 바뀌었다”는 가족 사칭 가능성이나 실제 기관 안내처럼 문맥을 읽어야 하는 경우에는 한계가 있다. 따라서 AI는 부가기능이 아니라 **애매한 문자의 의도와 사칭·압박 맥락을 해석하고, 60대 이상 사용자가 이해하기 쉬운 짧은 설명으로 바꾸는 핵심 수단**으로 사용한다.

서비스는 AI와 규칙엔진의 역할을 의도적으로 분리한다. AI는 `summary`, `risk_context`, `safe_next_action`, `uncertainty`를 JSON으로 생성해 “무슨 뜻인지, 무엇이 수상한지, 무엇을 확인해야 하는지”를 설명한다. 반면 돈·신원·계정에 직접 영향을 줄 수 있는 행동의 권한은 AI에 주지 않는다. 송금·이체, 인증번호 전달, 앱 설치, 원격제어가 감지되면 규칙엔진의 HIGH 판정을 AI가 낮출 수 없으며, AI가 높은 확신으로 안전하다고 답하더라도 최종 행동 권고는 결정론적 안전 규칙을 유지한다. 즉 **AI confidence ≠ user authorization**을 제품 정책으로 구현한다.

모두의 AI 실험실에서는 실제 제공 모델을 로그인 화면에서 확인한 뒤 `AI 안심매니저` 프로젝트를 만들고, 동일한 프롬프트와 최소 3개 이상의 대표 문자를 실행해 결과를 기록할 계획이다. 프로젝트 생성 화면, 정확한 모델 표시명과 프롬프트 설정 화면, 개인정보를 제거한 JSON 실행 결과 화면을 증빙으로 남긴다. 현재 저장소에는 모델 API를 추정해 하드코딩하지 않고 호출 함수를 주입받는 어댑터를 두어, 플랫폼의 실제 endpoint/SDK가 확인되는 즉시 기존 TypeScript 앱과 연결할 수 있게 했다. 플랫폼이 직접 연동 API를 제공하지 않는 경우에도 `문자 → 규칙 가드레일 → AI 맥락 해석 → JSON 구조 검증 → 최종 안전 응답`의 결합 구조를 그대로 유지한다.

안전성과 실패 대응도 AI 사용의 일부로 설계했다. 모델 장애, 응답 지연, 잘못된 JSON이 발생하면 AI 결과를 버리고 기존 규칙엔진으로 즉시 fallback한다. LOW 판정도 “안전 확정”으로 표현하지 않으며, 발신자나 기관의 진위를 실제로 확인하지 않은 경우 확인했다고 말하지 않는다. 문자 원문·개인정보·API 키는 저장소나 로그에 남기지 않는다. KISA/보호나라 데이터 연계 역시 실제 API와 이용 조건을 확인하기 전에는 구현 완료로 주장하지 않는다. 이 구조를 통해 AI의 문맥 이해 능력을 적극 활용하면서도, 시니어가 가장 위험한 순간에는 예측 가능한 규칙과 사람 확인 절차가 우선하도록 한다.
