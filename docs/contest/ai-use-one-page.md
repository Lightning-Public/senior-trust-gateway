# AI 활용 필요성·플랫폼 활용·안전 설계

`시니어 AI 생활매니저`가 해결하려는 문제는 고령자가 문자, 키오스크, 공공·생활 서비스 같은 디지털 환경에서 “이 내용을 믿어도 되는가, 지금 무엇을 해야 하는가”를 매번 스스로 판단해야 한다는 점이다. 기존 규칙엔진은 송금·인증번호·앱 설치·원격제어처럼 명확한 위험 신호를 빠르고 일관되게 차단할 수 있지만, 가족 사칭 가능성, 기관 안내, 복잡한 키오스크 화면처럼 문맥을 이해해야 하는 상황에는 한계가 있다. 따라서 AI는 **애매한 의도와 상황을 이해하고 60대 이상 사용자가 이해하기 쉬운 설명과 다음 행동으로 바꾸는 수단**으로 사용하되, 안전 권한은 AI와 분리한다.

공모전 Phase 0은 전체 생활매니저 가운데 가장 신뢰가 중요한 두 장면으로 범위를 제한한다. 첫째, `Trust Check`는 의심 문자와 디지털 요청의 의도·사칭·압박 맥락을 설명한다. 둘째, `Kiosk Safe Guidance`는 `Lightning-Public/kiosk_ar_assistant@3a7da8f`의 큰 안내·음성형 문구·포인터 UX 개념을 활용해 **병원 접수 한 장면**을 구조화된 화면으로 안내한다. 병원 Kiosk 데모는 카메라/CV/OCR 없이 접수 시작과 예약 선택을 안내하고, 주민등록번호 전체 입력 같은 민감정보 단계에서는 HIGH로 자동 진행을 중단해 직원 도움을 요청한다. 두 장면은 별도 앱이 아니라 `이해 → 위험 확인 → 쉬운 다음 행동 → 필요 시 사람 연결`을 공유한다. 단기 제출 범위는 Trust Check 80% + Kiosk 20%다.

서비스는 AI와 안전정책의 역할을 의도적으로 분리한다. Senior Trust Gateway는 위험등급, 공식 검증 수준, 권한정책과 사람 에스컬레이션을 담당한다. AI 출력 계약은 `summary`, `risk_context`, `safe_next_action`, `uncertainty`로 제한하며, 송금·이체·인증번호 전달·앱 설치·원격제어·개인정보·결제처럼 고위험 행동은 규칙엔진의 HIGH 판정을 AI가 낮출 수 없다. 즉 **AI confidence != user authorization**을 제품 정책으로 구현한다. 현재 AI 안전 레이어는 코드와 테스트로 검증됐지만, 확인된 실제 AIProvider가 없어 기본 UI 런타임에는 연결하지 않은 상태다.

모두의 AI 실험실에서 현재 확정된 활용은 `AitestbedVibeWorkflow`다. 바이브코딩으로 `시니어 AI 생활매니저` 화면을 생성·수정하고 소스를 다운로드해 현재 TypeScript prototype과 비교하며, 필요한 UI만 최소 포팅한다. 외부 AI 추론 API는 공식 문서, base URL·인증·모델·schema, 최소 실제 호출 probe, 외부 프로젝트/개인정보/상업 이용 범위를 모두 확인한 경우에만 `AIProvider` 뒤에 연결한다. `내 API 키` 화면만으로 추론 API를 추정하지 않는다. API 키는 브라우저 번들·Git·로그에 넣지 않고, 모델 장애·quota 초과·응답 지연·잘못된 JSON·모델 거부 시 결정론적 규칙으로 fallback한다.

이 구조는 공모전의 **문제 정의 및 제안 필요성**에는 고령자의 디지털 신뢰·접근성 문제로, **창의성 및 AI 활용 적절성**에는 AI 문맥 이해와 결정론적 권한통제를 결합한 구조로, **실현 가능성 및 완성도**에는 동작 중인 Trust Check, 병원 Kiosk 구조화 데모, aitestbed 바이브코딩 생성·다운로드 증빙, fallback 테스트와 CI 결과로 대응한다. 장기적으로는 문자와 키오스크를 시작으로 예약·행정·생활지원·가족 연결까지 확장해, 단순 챗봇이 아니라 **안심하고 일을 맡길 수 있는 시니어 AI 생활매니저**로 발전시키는 것이 목표다.
